# FIX-003 — the pump's halt is durable: what operators must know

Bench run `run-20261017T211949Z-30a6612c` (app `a2f962c8`) restarted the same failed activity 57 times in 28 minutes. The project store was refusing every write (FIX-002), so the failing activity left no row, and the pump's G-P12 stop was just a returned error. Thirty seconds later the sweep started a fresh pump chain into the same refusal. Nothing anyone could read said the cascade had stopped.

Since FIX-003, the pump **parks** on a failed activity instead of returning:

- It keeps its workflow id `{projectId}:nextActivity`, so the 30-second sweep's start is "already started" and the sweep skips the project (`pump sweep: project already cascading, skipped`).
- It keeps granting sibling activities their main-write lease and keeps observing their terminals, but starts nothing new.
- It carries the halt across continue-as-new.
- The project view reads `runState: "halted"` with `pumpHalt {activityId, cause, haltedAt}`. The activity reads `haltedByFailure`. Begin (`ExecuteNextActivity`) is refused with FailedPrecondition and the refusal names `ResumeProject`.
- **The only way out is the operator's resume**, `setProjectRunState(running)`. On a halted project that is not paused, the resume **writes nothing to the store**: it signals `operatorResumeRequested` to the pump. On a project that is both paused and halted, it records the resume first and then signals. A head-state write does NOT resume the pump.

The halt lives **only** in the pump's Temporal execution. The store may be the very thing that refused the failure, so the halt cannot be written there. That is the whole design, and it is also its one weakness.

## Before any drain, terminate or reset of `*:nextActivity:*`: read the halts first

Draining, terminating or resetting a halted pump **erases its halt**. The next sweep tick then starts a fresh chain, which dispatches the failed activity again. If the store still refuses writes, that is the pre-FIX-003 restart loop. So, before the `*:nextActivity:*` sweep in any drain:

```sh
# every running pump
temporal workflow list --namespace <ns> \
  --query "WorkflowType='constructionPumpNextActivity' AND ExecutionStatus='Running'"

# each one's halt (null when it is not halted)
temporal workflow query --namespace <ns> \
  --workflow-id '<projectId>:nextActivity' --type pumpHaltState
```

For each pump that answers with a halt, record the project id, `activityId`, `cause` and `haltedAt` in the drain log. Then, before un-pausing that project after the deploy, either fix the cause (for FIX-002's wedge, the one-time manual recovery of the state repo's checkout), or pause the project (`setProjectRunState(paused)`) so the restarted sweep leaves it alone until it is.

## Deferred (not in FIX-003)

- **Other error returns still end the pump.** A `pumpRecordBlocked` write the store refuses (verdictBlocked on an unwritable store), a non-NotFound head-state read error on a pump that is not halted, and a lease-delivery error each still return an error, so the sweep restarts the pump. The FIX-003 plan scoped only the G-P12, ActivityChildFailed and ActivityChildVanished arms.
- **The sweep log does not carry `halted=<activityId>`.** The sweep cannot see a halt without one extra Query Activity per project per tick. Each halted pump logs its own halt instead, and its start is refused as "already cascading".
- **A sibling lease granted while the pump is parked has no scenario.** The delivery harness narrows the plan to one construction activity. Covering this needs a two-activity arrangement.
- **Paused and halted at once has no scenario.** The code path (record, then relay) is covered only by review. A fourth resume path would need bindings on five components.
- **An orphaned row keeps reading `running` after a resume.** A row with `startedAt` and no outcome, left when a failWalk write was refused, is not re-selected (its start stamp excludes it), and once the halt is cleared it reads `running` with no execution behind it. The halt names it only while the halt holds.
- **Sibling birth contention now halts the project.** When the M0 seal starts many activities at once, their OpenActivity births race on one ref and some hit `MutateConflictExhausted`. This is the birth-contention earmark from 2026-10-10. Before FIX-003, the pump failed, the sweep restarted it 30 s later, and the next chain re-dispatched the rows that never got born, so construction recovered on its own. Since FIX-003, the first such failure halts the pump until an operator resumes it. The full delivery suite hit this in `commit-to-a-project-option-P1/P2`. Two fixes are open, and both need a ruling: batch-birth the rows in one commit (the earmark), or exempt a retryable CAS exhaustion from G-P12.
