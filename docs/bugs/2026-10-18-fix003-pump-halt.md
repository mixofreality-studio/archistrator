# FIX-003 — the pump's halt is durable: what operators must know

Bench run `run-20261017T211949Z-30a6612c` (app `a2f962c8`) restarted the same failed activity 57 times in 28 minutes. The project store was refusing every write (FIX-002), so the failing activity left no row, and the pump's G-P12 stop was just a returned error. Thirty seconds later the sweep started a fresh pump chain into the same refusal. Nothing anyone could read said the cascade had stopped.

Since FIX-003, the pump **parks** on a failed activity instead of returning:

- It keeps its workflow id `{projectId}:nextActivity`, so the 30-second sweep's start is "already started" and the sweep skips the project (`pump sweep: project already cascading, skipped`).
- It keeps granting sibling activities their main-write lease and keeps observing their terminals, but starts nothing new.
- It carries the halt across continue-as-new.
- The project view reads `runState: "halted"` with `pumpHalt {activityId, cause, haltedAt}`. The activity reads `haltedByFailure`. Begin (`ExecuteNextActivity`) is refused with FailedPrecondition and the refusal names `ResumeProject`.
- **The only way out is the operator's resume**, `setProjectRunState(running)`. On a halted project that is not paused, the resume **writes nothing to the store**: it signals `operatorResumeRequested` to the pump. On a project that is both paused and halted, it records the resume first and then signals. A head-state write does NOT resume the pump.

The halt lives **only** in the pump's Temporal execution. The store may be the very thing that refused the failure, so the halt cannot be written there. That is the whole design, and it is also its one weakness.

## Before any drain, terminate or reset of `*:nextActivity:*`: read the halts first

Draining, terminating or resetting a halted pump **erases its halt**. The next sweep tick then starts a fresh chain, which dispatches the failed activity again. If the store still refuses writes, that is the pre-FIX-003 restart loop. So, before the `*:nextActivity:*` sweep in any drain:

```sh
# every running pump
temporal workflow list --namespace <ns> \
  --query "WorkflowType='constructionPumpNextActivity' AND ExecutionStatus='Running'"

# each one's halt (null when it is not halted)
temporal workflow query --namespace <ns> \
  --workflow-id '<projectId>:nextActivity' --type pumpHaltState
```

For each pump that answers with a halt, record the project id, `activityId`, `cause` and `haltedAt` in the drain log. Then, before un-pausing that project after the deploy, either fix the cause (for FIX-002's wedge, the one-time manual recovery of the state repo's checkout), or pause the project (`setProjectRunState(paused)`) so the restarted sweep leaves it alone until it is.

## Deferred (not in FIX-003)

- **Other error returns still end the pump.** A `pumpRecordBlocked` write the store refuses (verdictBlocked on an unwritable store), a non-NotFound head-state read error on a pump that is not halted, and a lease-delivery error each still return an error, so the sweep restarts the pump. The FIX-003 plan scoped only the G-P12, ActivityChildFailed and ActivityChildVanished arms.
- **The sweep log does not carry `halted=<activityId>`.** The sweep cannot see a halt without one extra Query Activity per project per tick. Each halted pump logs its own halt instead, and its start is refused as "already cascading".
- **A sibling lease granted while the pump is parked has no scenario.** The delivery harness narrows the plan to one construction activity. Covering this needs a two-activity arrangement.
- **Paused and halted at once has no scenario.** The code path (record, then relay) is covered only by review. A fourth resume path would need bindings on five components.
- **An orphaned row keeps reading `running` after a resume.** A row with `startedAt` and no outcome, left when a failWalk write was refused, is not re-selected (its start stamp excludes it), and once the halt is cleared it reads `running` with no execution behind it. The halt names it only while the halt holds.
- **Sibling birth contention now halts the project.** RESOLVED by FIX-006 (row-scoped writes commute): the activityExecutionAccess and gitActivityStatusAccess row verbs no longer assert the project version, the store serialises read -> apply -> commit in a per-project in-process write queue and re-applies a ref-CAS lost to an outside writer itself (exhaustion is Transient, never Conflict), and every delivery scenario now fails if its pump ends halted. G-P12 was not weakened. FIX-006 earmarks: (A) batch-birth at the M0 fan-out as a commit-count optimisation, with its own born-without-a-child handling; conditional whole-document writes still wait in the queue behind a sibling herd under a 15 s StartToClose (convergent through retry, unmeasured on GitHub); group commit in the queue; a row version on git-status rows if a second same-row writer appears; promoting the queue to the platform (MutateSubtree) when a second git-as-DB RA needs it; the expectHalt allow-list measurement over the full suites.

## FIX-006 ruling 5 — folded in (2026-10-20)

Ruling 5's default was "earmark per-slot or conditional-re-validate guards; fold in now only if the conditional-verb test shows the facade's 3 attempts do not converge". Review measured that they do not: under a real fan-out `revokeM0Commitment` reads the whole project, then calls `RecordSdpReviewOutcome` at that Version with 3 attempts, and with 17 construction children writing rows through the queue it lost every attempt (P2 step 3 failed 2 of 5). The workflow's conditional writes (bound 20) can starve the same way. So it is folded in.

**Shape.** A main-scoped conditional verb names its *footprint*, the document members its decision depends on. It is refused only when one of those changed after the version its caller read. The check runs at the tip, inside the write queue. The contract parameter is unchanged (`expectedVersion` is still the version the caller read). Only its guard changed, so no caller, Activity signature or workflow changed.

| Verb | Guard (refused when any of these changed after `expectedVersion`) |
|---|---|
| CommitArtifactWithProvenance | its slot + phase |
| StageArtifactForReviewOnBranch, SeedReviewCommentsOnBranch (branch `""`) | its slot + phase |
| AcknowledgeStaleBasis | its slot + phase |
| RecordSdpReviewOutcome (M0 reject-all / revoke) | the sdpReview slot + phase |
| AdvancePhase | phase + every slot (the seal is decided on all of them) |
| RecordOperatorPaused, RecordOperatorResumed | operatorPaused, pauseReason + phase |
| RecordReviewPolicy | reviewPolicy |
| RecordTrackingPoint | constructionProgress |
| SetOperatingModel | operatingModel + phase |
| SetResearchInput | research + phase |
| CreateProject | exact: expectedVersion 0 and no document. The precondition genuinely is the whole document. It runs once, before any row exists, so nothing can starve it. |
| Any verb on a session branch; ReconcileBranchFromMain | exact project-version guard on the branch's own version. No row write rides a branch, so nothing there is starved. |
| StageTaskOutput (activityExecutionAccess) | unchanged: its live session-branch `expectedVersion` guard |
| The 10 row verbs | unchanged from FIX-006: no project version; the row's own version |

A version newer than the project's is always a Conflict.

**Mechanism.** `.aiarch/state/write_marks.json` is the store's own ledger. For each document member (per entry for `slots`, `activityExecution`, `activityGit`) it records the version of the last store write that changed it, plus a digest of its bytes. Every main write restamps it in the same commit as `project.json`; row writes stamp only their own row. It is a separate file, not a `project.json` member, because only main's store writes modify it, so 3-way merges of the state document always take main's copy and the envelope resolver never sees it. It is only ever conservative. An absent or unreadable ledger, a project Version moved outside the store, or a member whose bytes changed outside it (a merge keeps main's version) all read as "changed at the tip", which is the old exact guard for that one write. That write then re-baselines the ledger.

**Deploy.** No workflow code changed, so there is no `GetVersion` fence. The drain FIX-006 already requires (the row verbs' Activity argument lists changed) covers this change. A mixed-version rollout is safe in both directions. An old pod writes `project.json` without restamping the ledger, so new pods read every member as changed at the tip (exact guard) until their next write. An old pod ignores the ledger. Its whole-subtree write also drops the file, which only makes the new pods fall back to the exact guard once.

**Earmarks.**
- The platform stages a state commit file by file (`replaceSubtree` calls `Worktree.Add` per file, and each Add re-diffs the whole tree), and every commit carries the whole `applied_mutations/` ledger. A write's cost therefore grows with the number of writes before it. The 48-sibling test shows this directly, and an unbounded test herd stalled a run. This is a platform performance item (stage once, or prune or compact the dedup ledger), separate from this fix.
- `revokeM0Commitment` also reads its own activity row (the passed M0 round and its decidedAt). Rows are deliberately not in the sdpReview footprint, because that would re-admit the herd. What it depends on is safe without them: a Passed round's outcome and decidedAt are write-once, and the slot status it requires is in the guard.
