### FIXED `210658f1` — the CONSTRUCTION rail was switched ON on the local profile (R13)

The defect fix round 1 left behind, and the reason a "minimal" recognition at one use site was not enough: **construction reads the ONE repo resolver TWICE.**

- `constructRepoTarget` (the dispatch venue) was taught to recognise the GitLocal ref in round 1 (`0e355c41`).
- `railLifecycleEnabled` (the rail LIFECYCLE) was not. It answered `rail != nil && repo != nil`, and on the local profile BOTH are non-nil — `main.gen.go:562` binds `NewGitLocalSourceControlAccess`, and the collapsed hook resolves every project — so `wfDeps.RailEnabled` went `false` (its value at `4baed01a`, where `ConstructionManagerRepo()` returned nil) → `true`.

**The failure scenario, in order.** `RailEnabled=true` ⇒ `gitEnabled()` returns `(GitLocalRef, true)` ⇒ `startedCred` takes the **CLOUD** arm and calls `mintCred`, putting a NEW durable `sourceControlAccess.getInstallationToken` command into every local construction history (a credential that means nothing against a `file://` repo, and a command no recorded history has — `TMPRL1100` for anything in flight); and `runLocalMergeStep`'s `|| wf.RailEnabled` guard makes the local merge **SKIP**, so no local activity branch ever lands on `main`. Cloud was never affected. `hooks.go`'s own comment had declared exactly this outcome unacceptable.

**The fix** (server commit 1 of the final wave): both readers share ONE recognition — `isGitLocalVenue` (`constructactivity.go:110`) — and `RailEnabled` is derived from what the resolver **ANSWERS** rather than from the deps being non-nil, which makes it a per-project question (`func(ProjectID) bool`, defaulted to `railDormant` at `deliverymanager.go:9775` so an unwired slice cannot nil-call it). The two non-local arms keep their pre-collapse verdicts exactly: a catalog-resolved repo is rail-enabled, and a PR-rail boot whose catalog **misses** a project stays rail-enabled (dormant for that project anyway, but the local merge must not substitute for the rail on a rail boot). Pinned by `Test_RailLifecycleEnabled_ReadsWhatTheResolverAnswers` (six reachable combinations), `Test_DeliveryManager_LocalProfile_ConstructionRailDormant_DesignRailsResolveGitLocal` (the construction half dormant AND `gitEnabled` false while BOTH design halves still resolve the GitLocal ref), `Test_DeliveryManager_CatalogResolver_ConstructionRailEnabled`, and `Test_DeliveryManagerRepo_LocalProfile_AnswersTheRefConstructionRefuses` (`cmd/server` — the hook must answer with the exact ref construction refuses, for every project, or a look-alike would sail through). Mutation-checked: with the recognition disarmed, two of them fail. All 19 replay fixtures stay green — no new command enters any recorded history.

**The earmark that survives it:** `Test_RailLifecycleEnabled_RequiresRailAndRepo` fed `repo=nil` as "the local profile" — an input the collapsed hook can no longer produce — and its doc comment asserted that now-false premise, which is how a green table coexisted with the defect for a whole wave. **A test whose inputs a real boot cannot produce is not a gate.** When a composition-root hook collapses, re-derive the affected tables from the profiles that actually exist.

## Armed but not recoverable — two degradations 4b owns

1. **`applyRecovering` cannot recover a per-activity `Conflict`.** Its re-read arm holds only the PROJECT version, so a genuinely external row writer (the pump's `pumpnextactivity.go:163 ConstructionTransitionRecordActivityFailed`, or an operator note filed through the API while a child runs) drives the loop to `MutateConflictExhausted` instead of a re-read. Bounded, loud, and nothing is corrupted — and unreachable today with one child per project. **It stops being an edge case the moment 4b's pump starts more than one child**, and R5 explicitly reserved that ruling for the pump's design. The missing capability has a name: re-read the ROW on a row-level Conflict.
2. **The design rails' seed read degrades silently.** On a **non-`NotFound`** read failure while the row exists, `seedRoundBaseFromLedger` returns early, `activityVersion` stays 0, and the session is admitted **unread** — so its `OpenActivity` applies (bumping the row N → N+1) while the session's own counter goes 0 → 1, and the next `OpenReviewRound` Conflicts, is logged only, and leaves the session on the slot ledger alone (`coauthorartifact.go:3934`, `coauthorphase2artifact.go:2097`). Correct degradation for a best-effort rail today. **Same missing capability as (1)** — fix them together.

Two more things hold the CAS up by hand, and 4b should retire both: the **ten `rowAdvanced()` call sites** in construction plus five in each design rail are a manual invariant (a new verb that writes the row and forgets to advance re-creates the bug the mutation test caught), and **`projectdesign` has no behavioural detection at all** — no Phase-2 kind has a review task in its pinned lifecycle, so its threading is correct-by-symmetry with systemdesign and untested. 4b's facet retirement removes four of the ten sites outright.
