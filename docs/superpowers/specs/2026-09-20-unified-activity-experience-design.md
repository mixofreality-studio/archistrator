## 1. Thesis

System design, project design and construction are one workflow: **agents generate artifacts, agents and humans review them, and an activity advances through its own little life cycle** (Righting Software App. A). Requirements, Architecture and Project Design are simply activities 1–3 of the project network (Table 11-1), fenced from construction by milestone M0 (ch. 11 "About Milestones"). The product stops having three phase rails with three managers and three UIs; it has one plan of activities, one manager, one review engine, one staging/review rail, and one full-screen Activity Experience.

## 2. Vocabulary

Extends the R3 naming ruling in `projectstateaccess.go` (the bare word "phase" stays banned).

- **Activity** — a node of the project network. Has a type, a **lifecycle** and a state.
- **LifecyclePhase** — Figure A-2 grouping of tasks with a weight and a binary exit criterion (its gate task). Earned-value unit.
- **Task** — a node of the lifecycle DAG. `kind ∈ {dispatch, review}`. A review task may be `gate: true` for its LifecyclePhase.
- **Attempt** — one execution of a task (exists today, append-only).
- **Revision** — NEW. Revision *n* of a LifecyclePhase = the *n*-th work-task attempt that reached the gate + the gate attempt that judged it. A send-back opens revision *n+1*. Failed/retried attempts inside a revision are sub-attempts of that revision, not new revisions.
- **Episode** — the trace of one agentic attempt (unchanged; `TargetRef = AttemptID`).

## 5. Server design

### 5.1 Parent: the pump (`{projectId}:pump`)
Walks the network; starts a child for **every** eligible activity (dependencies Done, M0 fence honoured), not one at a time; reacts to child completion by signal rather than blocking on `child.Get`. Singular per project (lands on top of the `pump-singular-per-project` fix). The plan derivation emits activities 1–3 and M0 as a fixed prefix; M0 `dependsOn` projectDesign and fans out to every construction root.

**AMENDED 2026-09-29 (stage 4b2, SHIPPED). The pump GRANTS A LEASE; it does not do the merge. `child.Get`'s blocking wait is gone and `ExecuteChildWorkflow` STAYS.** Commits `b84098eb` (the pump) + `aa977ae9` (fix round) + `37b0e768` (the wire-form fix the fixture capture forced). The id is unchanged — `{projectId}:nextActivity` (`pumpWorkflowID`), not a re-key.

**What replaced the blocking wait, and what was deliberately kept.** The dispatch path drops only the BLOCKING `.Get`: the run still starts each child with `ExecuteChildWorkflow` and then SELECTS over the N child futures alongside the lease/finish signal channels and a 30 s reconcile timer. That keeps all four affordances `child.Get` was carrying for children started in THIS run — ordering, **error propagation**, `PumpStatus.open` liveness, and guaranteed delivery — with no new RA producer, because a signal carries no error channel and `deliveryActivity` has no failure-signal producer. Futures do not survive a `ContinueAsNew`: for children that predate one, the reconcile tick plus Temporal's own execution state are authoritative, which is the pump's stated doctrine (**no fact comes from a signal alone**) holding on both halves. Two rules the fix round had to make explicit: a FINISH signal is a **lease release**, never a completion — `markFinished` was split into `releaseLease` (what a signal may do) and `markFinished` (only a fact the pump established itself: a resolved future, or the terminal row) — because a failing merge tail sent `activityFinished{Completed}` from a `defer` before returning its error, and the pump went QUIESCENT while the child failed. And keying on the outcome CANNOT work: `ActivityOutcome` is `{Unknown, Completed, Skipped, TakenOver}` and a clean give-up and a broken tail both report `Unknown`.

**THE MERGE STAYS IN THE CHILD — and that is the design, not a shortcut.** §5.1's "pump-as-merge-queue" phrasing (architect Ruling 3(b)) would put the main-write MERGE in the parent. It does not go there: `finalizeWalk`'s tail brings a **gate, an inbox and a gate ledger** with it — the merge is preceded by `holdForMergeApproval`, which awaits an operator decision routed through the child's OWN per-task signal inbox (§5.2 fact 1), sits in the same walk as the per-review-coroutine `*gateLedger` (fact 2), and is the one hold that opens no review round, which is why the façade's own stage check still guards it. Moving that up would put all three in the pump, which **§10 forbids**: the pump is the scheduling spine and per-activity behaviour lives in data and strategy inside the child (the God-manager risk, and §5.2's "the walker names no type" rule, are the same rule read from two ends). So the pump serialises main writes the only way it can without absorbing the child's lifecycle: **it hands out an admission token.** `activityLeaseRequested` → `pumpGrantLease` → `activityLeaseGranted` → the child runs its tail → `activityFinished` releases it. The lease sits **on top of** the row-level CAS and the branch-file version guard; it never replaces them, and the child's request **fails open** (it logs and runs the tail unleased after a 2 h budget) because failing a completed activity's merge because the admission queue is unreachable would be worse than the pre-wave state.

**Two limits of the lease that belong in the design, not only in an earmark.** (1) **Its scope is per pump CHAIN, not per project.** `LeaseHolder` lives in `pumpState`/`pumpInput`, so it survives a `ContinueAsNew` and nothing else; any run that exits while a lease is held (a pause while parked, a child failure, any error return) leaves the next chain with an empty holder, and that chain can grant a second lease while the first child is still in its merge tail. Only the row-level CAS holds there — **"fails open" is the NORMAL state after any pump restart, not a rare fault path.** (2) **The lease had never run in production before this wave shipped.** All three lease messages ride `messageBus.deliverSignal`, which sends raw `[]byte` (binary/plain), and all three were received into concrete structs, so the SDK dropped every one; the whole 4b2 lease was INERT until `37b0e768`. It failed open, so nothing went red. Details, and the fifth `deliverSignal` producer that carries the same defect as a LIVE billing/operations bug, are in `docs/bugs/2026-09-28-stage4b2-earmarks.md`.

**No read-amplification win is claimed, and none may be.** The pump **re-reads the whole aggregate on every wake-up** — 1.17 MB, every 30 s while parked — because the CHILD writes head state and the frontier genuinely moves, so deriving the frontier from carried in-memory state is stale by construction. The "27 reads → 1" figure from planning was withdrawn as unreachable: `readProject` ran once per pump RUN, so 27 reads meant 27 RUNS (ContinueAsNew per dispatch), and a mostly-serial 30-activity DAG simply becomes ~27 wake-ups inside ONE run. **The real 4b2 win is the history churn of per-dispatch ContinueAsNew, not the read count**; a test asserts `reads >= 2` so the claim cannot creep back in.

**Four structural facts the child's implementation forced, each of which the spec's pseudocode above does not show:**

1. **A per-child signal ROUTER, not shared channels read by task coroutines.** The four signal channels (`taskDecision`, `setCommentStatus`, `operatorOverride`, `redraft`) are opened ONCE by the entry func and handed to one router coroutine, which forwards each message to the NAMED task's own inbox (capacity 64). Concurrent coroutines receiving one shared channel steal each other's signals. `deliver` is **non-blocking** (`SendAsync`, overflow to a `pending` map) because a blocking `Send` on a retired task's full inbox WEDGES the walk — measured: *"trying to block on coroutine which is already blocked"*, the hazard verbatim, now a shape case. Every receive loop calls `drainPending` at the top; a misroute is parked in a LOCAL `deferred` slice and re-offered once when the loop ends, never returned to `pending` (a re-queue spins, and each iteration builds a fresh timer).
2. **One `*gateLedger` per review coroutine.** The single-valued `constructState.gate` would have made two concurrent gates overwrite each other's round id and decide the wrong round.

### 5.5 Authorization of body-carried project ids (ruling, 2026-09-25)

Moving `StartProject`'s `projectID` off the path and into the body (§4) moved its generated authorization with it. `httpgen`'s convention is that a **path** id param yields `security.ResourceRef{Kind: "project", ID: <the id>}` and **no** path id yields `{Kind: "<manager>Catalog", ID: principal.Subject}` — so the adopt arm was presenting the authorizer with a ref that did not name the project being adopted. Not exploitable under the interim `authenticatedOnlyPDP`, but it destroys the resource ref a real (Cedar) PDP would decide on, which is the whole reason `cmd/server/authz.go` keeps the seam wired.

**The ruling: the generator is NOT taught to read a body id.** A path id is the convention's identity signal; reaching into a request wrapper for an optional id would make every body-carried id a silent authorization surface. A body-carried project id is authorized instead by a **project-scoped Manager decorator at the composition root** (`cmd/server/hooks.go`, installed by `WrapManagers`), which re-asks the same question with the same verb against `{Kind: "project", ID: <body id>}` and answers `Unauthorized` (403) on deny or on an unreachable engine. `projectScopedDeliveryManager` is the instance; `projectScopedOperationsManager` is its precedent, and the guard sits at the composition root rather than inside the Manager façade because the derivation does — the Manager holds no `security.Security` dep, and one built inside it would get framework-go's deny-by-default `defaultPolicyDecisionPoint`. Because `WrapManagers` hands the same instance to the REST handlers and the MCP tools, the guard covers both transports; the MCP surface authorized nothing of its own before.

**This is the convention for any future body-carried id**, and it is a must-ship-together member (§8): a guard the composition root forgets is not a guard, so the wiring is pinned by its own test. Both arms landed in 4a — `StartProject`'s adopt branch and `QueryProjectView`'s `projectId`, the one read of every project over all six project-addressed kinds. Two cases are deliberately NOT guarded: `QueryProjectView{kind:"projects"}` carries an owner and no project id — it IS the catalog listing, so the catalog decision is exactly the question it asks — and an empty non-nil id falls through to the Manager's `ContractMisuse`, because denying it would turn a malformed query into a permissions error.

**Audited across all twelve ops at 4a:** the generated handlers hold exactly two catalog-scoped refs (`start-project`, `query-project-view`) and ten project-scoped ones from path params, and **no other op names a project in its body** — the only inbound body-side `projectId` members in the contract are `startProjectRequest`'s and `ProjectViewQuery`'s. Re-run that audit whenever an id leaves a path.
